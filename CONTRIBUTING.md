# How to participate

Welcome! You can contribute without joining the GitHub organization. Start with a public issue; an implementation is not required.

## Useful first contributions

- Explain a real-world use case using fictional or sanitized data.
- Identify ambiguity in the white paper, citing its section or page.
- Describe an interoperability requirement and how to test it.
- Review a proposal from a domain, usability, or implementation perspective.
- Suggest a focused documentation correction through a pull request.

## Open an issue

Search existing issues first and add to an existing discussion when appropriate. Prefix a new issue title with `Question:`, `Use case:`, `Proposal:`, or `Editorial:`.

For a proposal, include:

1. **Problem:** Who encounters it and why does it matter?
2. **Source:** Relevant white-paper section or existing issue.
3. **Proposed change:** Concrete behavior or text; distinguish new ideas from the paper.
4. **Example:** A small example showing expected behavior.
5. **Alternatives:** Other approaches and their tradeoffs.
6. **Compatibility:** Effect on other proposals or implementations.
7. **Validation:** What evidence or test would show the proposal works?
8. **Open questions:** Decisions still needed.

If you are new, introduce the area you would like to help with in a `Question: How can I help with ...` issue. Do not post private contact details or confidential enterprise data.

## Submit a pull request

Fork the repository, create a branch, and make a focused change. Link the issue in the pull request and explain the change and how you checked it. For substantive technical changes, discuss the issue before investing in a large implementation. Include examples and expected validation results when relevant.

Keep the published September PDF unchanged. Propose corrections in an issue; a later paper edition should have a distinct filename and an explanation of the changes.

## Review constructively

State whether a comment is a question, suggestion, or blocking concern. Explain blocking concerns with examples and a possible resolution. Disclose relevant affiliations or implementation interests when they help others assess a proposal. Critique ideas respectfully and avoid personal attacks.

## What happens next

Maintainers acknowledge and categorize issues, help refine proposals, and publish their disposition: accepted into a working draft, needs revision, deferred, or declined with reasons. There is no guaranteed response deadline during community formation.

See [GOVERNANCE.md](GOVERNANCE.md) for review windows, authority, objections, and reconsideration. Membership and commit access are separate from participation and do not confer standards voting rights.

## Contribution policy status

Only submit material you are entitled to share publicly. Do not submit third-party confidential material. No project-specific license, patent grant, or contributor agreement is established by this guide; those policies remain open founding decisions. Discuss substantial specification or code contributions with the maintainers while those terms are being settled.
